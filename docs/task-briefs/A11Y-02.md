# A11Y-02 — Terminology, accessibility, density, and desktop hardening

## Goal and boundaries

Standardize English decision terminology, move specialist jargon into progressive help, and harden the established desktop experience for accessible keyboard, focus, status, chart, and table use. Establish desktop density rules without redesigning information architecture. Tablet and mobile-specific work are out of scope. Do not change owner scope, evidence values, scoring, provider behavior, or immutable historical records.

## Acceptance

- Decision labels use consistent English terminology, with jargon explained through progressive help rather than replacing exact evidence labels.
- Desktop decision surfaces provide visible focus, keyboard-operable controls, labels for inputs and interactive charts/tables, announced loading and status changes, and non-color alternatives for states and exact values.
- The established interfaces remain usable at 200% zoom and approximately 1440px desktop width with long English, Romanian, and Russian stored evidence text.
- Density rules preserve readable hierarchy, horizontal table access, exact values, and explicit empty, partial-data, success, and error states.
- Focused frontend and feature coverage verifies critical keyboard, focus, label, status, long-text, zoom/density, and documentation behavior.

## Applicable decisions

- D-038: Desktop keyboard access, focus behavior, exact visible values, and accessibility remain required.
- D-041–D-042: Mixed, partial, unavailable, estimated, and calculated outcomes require explicit labels and non-color alternatives.
- D-005–D-008: Owner-private state and authorization behavior must not be weakened by interface changes.

## Initial inspection targets

- Shared button, dialog, table, badge, alert, chart, pagination, and data-state primitives.
- Desktop decision surfaces introduced or materially redesigned in the Phase 19–21 workflow tasks.
- Existing focused frontend accessibility/interface tests and feature tests for those surfaces.

## Relevant contracts and UI

- Preserve existing Form Requests, policies, and domain boundaries; this task changes presentation and interaction unless a test exposes a necessary accessibility-safe boundary correction.
- Keep selection and navigation state owner-private, bounded, and recoverable; never expose hidden state only through color or hover.
- Tables and charts must retain exact visible alternatives and keyboard paths while dense desktop layouts preserve usable overflow behavior.
- All visible loading, success, empty, partial-data, unavailable, and error outcomes need accessible text equivalents.

## Focused verification

- Exact frontend tests for keyboard operation, focus restoration, labels, live status, long stored text, non-color state labels, and desktop density behavior.
- Exact feature tests only where interface accessibility requires server-provided labels or state changes.
- Formatter, lint, and type checks only for changed files.
